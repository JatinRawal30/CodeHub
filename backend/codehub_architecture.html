This diagram illustrates the high-speed batch execution cycle where all test cases are processed in parallel on Judge0 worker nodes.

    actor User as Client / User

    Backend->>DB: 1. Create Submission (verdict: "Pending")
    Note over Backend,DB: 💾 Code safely preserved in MongoDB!

    Note over Backend,Judge0: 2. Single Parallel Batch Dispatch
    Backend->>Judge0: POST /submissions/batch (All test cases in 1 request)
    Judge0-->>Backend: [{ token: "t1" }, { token: "t2" }, { token: "t3" }]

    Note over Backend,Judge0: 3. Non-blocking Result Polling
    loop Until all test cases finish (status.id > 2)
        Backend->>Judge0: GET /submissions/batch?tokens=t1,t2,t3&base64_encoded=false
        Judge0-->>Backend: Evaluation Status (In Queue / Processing / Done)
    end

    Note over Backend,DB: 4. Verdict Evaluation & Update
    Backend->>Backend: Evaluate outputs, peak executionTime & memory
    Backend->>DB: Update Submission document (Verdict, Time, Memory, Tests)
    alt If Verdict == Accepted
        Backend->>DB: Update user.problemsSolved ($addToSet)
    end

    Backend-->>User: 200 OK { verdict, testCasesPassed, executionTime, memory }

High-Frequency Interview Questions & Answers

📌 Q1: Why did you use base64_encoded=false when fetching results from Judge0?
By default, Judge0 returns outputs (stdout, stderr, compile_output) encoded in Base64 strings to safely transport binary or non-ASCII characters. Since our coding platform operates on standard plaintext UTF-8, setting base64_encoded=false instructs Judge0 to return raw plaintext strings directly. This eliminates unnecessary Buffer.from(str, 'base64') decoding overhead on every test case in the backend.
📌 Q2: How does Batch Submission improve scalability compared to sequential execution?
Sequential Execution: If a problem has 10 test cases, sending them 1-by-1 requires 10 roundtrip HTTP requests. If each takes 600ms, user latency is 6+ seconds.
Batch Mode (/submissions/batch): We send all 10 test cases in 1 single POST request. Judge0 executes them concurrently across worker threads. Our backend polls once or twice and receives all 10 results in ~1 to 1.5 seconds (an ~80% latency reduction).
📌 Q3: How do you prevent users from inspecting hidden test cases?
We implement Field Projection Filtering at the MongoDB query layer. When a public user fetches problem details via GET /api/problems/:id (or /get/:id), the query explicitly executes .select("-hiddenTestCases -referenceSolution"). Hidden test cases are only read into server memory during submission evaluation and never leave the backend.
📌 Q4: How is malicious user code prevented from compromising the server?
User code is never executed directly on the Node.js application server. Execution is delegated to Judge0, which encapsulates every run in an isolated Linux sandbox using isolate (cgroups, namespaces, chroot jail, and seccomp filters). This enforces strict CPU time limits, memory limits, and disables unauthorized network/filesystem access.
📌 Q5: How does your Authentication & Token Rotation (RTR) system work?
We use a dual-token strategy with Redis:
1. Access Token (15m): Stateless JWT passed in the Authorization: Bearer header.
2. Refresh Token (7d): Stored in an httpOnly, sameSite: strict cookie to prevent XSS.
3. Token Rotation (RTR): On /api/auth/refresh, the existing refresh token in Redis is destroyed, and a new token pair is generated.
4. Logout Blacklisting: On logout, the access token's remaining TTL is blacklisted in Redis to prevent reuse.
📌 Q6: How do you prevent duplicate entries when tracking solved problems?
We use MongoDB's atomic $addToSet operator: user.findByIdAndUpdate(userId, { $addToSet: { problemsSolved: problemId } }). This guarantees mathematical set semantics—no matter how many times a user resubmits an accepted solution, the problem ID is only stored once.
📌 Q7: What happens if code enters an infinite loop or allocates excessive memory?
- Infinite Loop: Judge0 terminates the execution when cpu_time_limit expires and returns Status ID 5 (Time Limit Exceeded).
- Memory Overflow: Linux cgroups abort the process with Status ID 7-12 (Runtime Error).
Our backend captures these status codes and returns a structured verdict without blocking Node.js.
📌 Q8: Why do you store the submission with status "Pending" before sending to Judge0?
1. Zero Data Loss: If Judge0 crashes or experiences a network outage, the user's submitted code and timestamp are already safely persisted in MongoDB.
2. Fault Tolerance: If an exception occurs, the submission record is updated with "Runtime Error" / "Internal Error" and the specific failure reason, rather than disappearing silently.
3. Queue Readiness: This decouples submission intake from execution, making it ready for asynchronous background worker queues (e.g., BullMQ / Redis).
